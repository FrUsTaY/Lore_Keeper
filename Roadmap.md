# Roadmap – «Нарративный Архивариус» (Lore Keeper)

## 1. Конечный продукт (Vision)

**Что это?**  
Десктопное приложение для Windows (в перспективе – кроссплатформа), которое автоматически ведёт «дневник приключений» по вашей игре. Оно делает скриншоты экрана, распознаёт текстовые подписи (названия квестов, имена NPC, локации, ключевые диалоги), а затем превращает этот сухой лог в художественный рассказ от первого лица с помощью локальной LLM (запущенной через LM Studio).

**Для чего?**  
- Сохранять эмоции и сюжетные моменты в красивой литературной форме без ручного записывания.  
- Делиться эпичными историями из игр в соцсетях.  
- Пересматривать свои выборы и развивать собственный нарратив.  

**Главные принципы:**  
- Полностью офлайн – никаких платных облачных API.  
- Работает даже на слабом ПК во время игры (только лёгкий OCR).  
- Тяжелая генерация происходит по требованию пользователя (или в фоне, когда ПК свободен).  
- Бесплатно навсегда (MIT-лицензия).

  - ⚠️ **Версия Python:** строго зафиксировать на **3.11.5**.
- [ ] Определить формат хранения «событий»: `JSON`-лог с полями: `timestamp`, `screen_text` (все распознанные строки), `game_window_title`, **`schema_version`** (число — чтобы будущие изменения формата лога в Фазе 4 не ломали парсинг старых сессий).

### Фаза 1 – Консольный прототип с умным захватом (MVP #1) (4–6 дней)

**Цель:** Создать консольное приложение, которое автоматически собирает значимые игровые события (тексты квестов, диалоги, названия локаций) без потери контента, используя адаптивную частоту сканирования и кольцевой буфер. Всё работает на CPU, без LLM.

---

#### Задачи:

- [ ] **1.1 Модуль `screen_capture.py`**
  - Функция `grab_screen()` – делает скриншот активного окна игры с помощью `mss` (быстрее, чем PIL).
  - Функция `compute_hash(image)` – вычисляет перцептивный хеш (через `imagehash.phash`) для быстрого сравнения кадров.
  - Функция `get_roi(image, region)` – вырезает заданную область (прямоугольник) из скриншота для OCR.

- [ ] **1.2 Модуль `roi_detector.py` (опционально, но сильно повышает качество)**
  - При первом запуске анализирует 10–20 кадров, ищет статичную область внизу экрана (тёмный прямоугольник с текстом) – это диалоговое окно.
  - Определяет координаты этой области и сохраняет в конфиг.
  - Если область не найдена – использует всю нижнюю треть экрана как ROI по умолчанию.
  - ⚠️ **Известное ограничение MVP:** многие игры показывают уведомления о квестах/лутe в углах экрана (toast-нотификации), а не только в нижней трети. ROI, ограниченный низом экрана, их пропустит. Для MVP это приемлемо, но стоит явно задокументировать как ограничение, а не молчаливый баг.

- [ ] **1.3 Модуль `ring_buffer.py`**
  - Реализует кольцевой буфер на `collections.deque` с максимальным размером 30–60 элементов (последние 6–12 секунд скриншотов при частоте 0.2с).
  - Хранит для каждого кадра: временную метку, хеш, уменьшенную копию скриншота (для последующего OCR).
  - Метод `get_last_n(n)` – возвращает последние N кадров.

- [ ] **1.4 Модуль `trigger_manager.py`** (самый важный)
  - Запускает бесконечный цикл с частотой **0.2 секунды** (5 раз в секунду) – это дешёво, просто захват и хеш.
  - Сравнивает текущий хеш с предыдущим. `imagehash.phash` возвращает **расстояние Хэмминга** (целое число бит), а не проценты — порог нужно считать как `hamming_distance / hash_size` (например, для 64-битного хеша `hamming_distance / 64`). Если нормализованное изменение > порога (например, 10%) – фиксирует **событие начала изменения**.
  - При фиксации события:
    - Переключает режим сканирования в **активный** (частота OCR теперь 1 раз в секунду, но только по ROI).
    - Запускает OCR на текущем кадре (из буфера) и на каждом следующем, пока хеш снова не стабилизируется (нормализованное изменение < 5% на протяжении 2 секунд).
  - После стабилизации возвращается в фоновый режим (только хеши, OCR не запускается).
  - Все распознанные тексты передаёт в `event_logger.py` с временной меткой.

- [ ] **1.5 Модуль `ocr_engine.py`**
  - Инициализирует Tesseract OCR с параметрами по умолчанию.
  - Функция `extract_text(image)` – принимает изображение (или ROI), возвращает список распознанных строк.
  - Добавляет простую постобработку: удаляет дубликаты (если текст полностью совпадает с предыдущим распознанным – игнорирует), фильтрует слишком короткие строки (меньше 3 символов – шум).

- [ ] **1.6 Модуль `event_logger.py`**
  - Принимает события от `trigger_manager` (текст + время).
  - Сохраняет их в список в памяти.
  - Каждые 10 событий (или раз в минуту) делает сброс в JSON-файл `logs/raw_events_<сессия>.json` для защиты от потери данных.
  - Структура записи: `{"timestamp": "2026-07-09T12:34:56", "text": "Взято задание: Убить 10 волков"}`.

- [ ] **1.7 Основной скрипт `main.py` (консольный)**
  - Запускает все модули в одном потоке (или в двух, если вынести OCR в отдельный поток, чтобы не блокировать захват).
  - Реагирует на нажатие `Ctrl+C` – корректно завершает цикл, сохраняет буфер и выгружает OCR-модель.
  - Выводит в консоль отладочную информацию: количество захватов, срабатываний OCR, текущий режим (активный/фоновый).

- [ ] **1.8 Тестирование на разных играх**
  - Проверить на оконных и полноэкранных режимах.
  - Проверить работу с разными шрифтами (если OCR плохо читает – добавить предобработку через OpenCV: увеличение контраста, бинаризацию).
  - Замерить потребление CPU в фоновом режиме (должно быть < 5% на одном ядре) и в активном (< 20%).

---

#### Результат фазы 1:
- Консольное приложение, которое запускается, висит в трее (или в консоли) и собирает лог событий в JSON.
- Никаких пропусков диалогов или квестов, благодаря детектору изменений и буферу.
- На слабом ПК работает без лагов, так как тяжёлый OCR включается только когда это действительно нужно.

### Фаза 2 – Интеграция с LM Studio и генерация историй (MVP #2) (4–5 дней)

**Цель:** Создать модуль, который принимает собранный лог событий (из Фазы 1), превращает его в связный художественный рассказ с помощью локальной LLM, запущенной через LM Studio, и сохраняет результат в удобном формате. Генерация должна работать как в ручном режиме (по запросу), так и в автоматическом (по окончании игровой сессии). Вся логика вынесена в отдельные модули, чтобы не смешивать с захватом экрана.

---

#### Задачи:

- [ ] **2.1 Модуль `config_manager.py`**
  - Читает конфигурационный файл `configs/lm_studio_config.json` с параметрами:
    ```json
    {
      "api_url": "http://localhost:1234/v1/chat/completions",
      "model": "qwen2.5-1.5b-instruct",
      "temperature": 0.8,
      "max_tokens": 1500,
      "timeout": 120,
      "genre": "fantasy"  // по умолчанию, но пользователь может выбрать в GUI
    }
    ```
  - Предоставляет методы для получения и обновления параметров (потом пригодится для GUI).
  - Проверяет доступность сервера LM Studio (пинг по `/v1/models`).

- [ ] **2.2 Модуль `prompt_builder.py`** (ключевой для качества)
  - Функция `load_events_from_log(filepath)` – читает JSON-лог, возвращает список событий с временными метками и текстом.
  - Функция `filter_events(events, max_events=100)` – ограничивает количество событий (чтобы не переполнить контекст модели). Стратегия:
    - Если событий больше max_events, берём последние N (самые свежие), т.к. они наиболее важны для окончания сессии.
    - Альтернативно: равномерно прореживаем, сохраняя ключевые моменты (можно добавить позже).
  - Функция `build_system_prompt(genre)` – возвращает системную инструкцию для модели на основе жанра:
    - *Пример для фэнтези:* *«Ты — опытный писатель-новеллист, специализирующийся на эпическом фэнтези. Твоя задача — превратить сухой список игровых событий в захватывающий рассказ от первого лица. Используй яркие метафоры, описывай чувства героя, добавляй драматизм. Пиши на русском языке, литературным стилем, избегай канцеляризмов. Рассказ должен быть связным, с плавными переходами между сценами.»*
    - Для киберпанка, реализма и т.д. – разные варианты.
  - Функция `build_user_prompt(events, genre)` – формирует сам промпт, который будет отправлен модели:
    - Вставляет в шаблон отфильтрованный список событий (каждое с временем).
    - Шаблон: *«Ниже приведены события, произошедшие с игровым персонажем в хронологическом порядке. Напиши на их основе рассказ от первого лица. События: [список]. Рассказ:»*.
  - Возвращает полный промпт (system + user) в формате, ожидаемом LM Studio (см. API).

- [ ] **2.3 Модуль `lm_studio_client.py`**
  - Класс `LMStudioClient` с методами:
    - `__init__(config)` – принимает конфиг.
    - `check_health()` – отправляет GET-запрос на `http://localhost:1234/v1/models` – если ответ 200, значит сервер жив.
    - `generate(prompt: dict)` – отправляет POST-запрос на `/v1/chat/completions` с телом:
      ```json
      {
        "model": "qwen2.5-1.5b-instruct",
        "messages": [
          {"role": "system", "content": "системный промпт"},
          {"role": "user", "content": "пользовательский промпт"}
        ],
        "temperature": 0.8,
        "max_tokens": 1500
      }
      ```
    - Обрабатывает ответ: извлекает текст из `response['choices'][0]['message']['content']`.
    - Обрабатывает ошибки: таймаут, соединение отклонено, ошибка модели – возвращает исключение с понятным сообщением.
    - ⚠️ Добавить простую retry-логику: 1–2 повторные попытки с коротким таймаутом (5–10 сек) для `check_health()`, прежде чем показывать пользователю ошибку — иначе 120-секундный таймаут превратит любой временный сбой в долгое зависание.
    - Логирует все запросы и ответы (в папку `logs/lm_studio_requests.log` для отладки).

- [ ] **2.4 Модуль `story_generator.py`** (оркестратор)
  - Функция `generate_story_from_log(log_path, output_path=None, genre=None, max_events=100)`:
    - Загружает конфиг.
    - Проверяет доступность LM Studio (если нет – выбрасывает исключение с инструкцией запустить LM Studio).
    - Загружает события из лога.
    - Фильтрует события через `prompt_builder`.
    - Строит промпт.
    - Создаёт экземпляр `LMStudioClient` и отправляет запрос.
    - Получает ответ.
    - Сохраняет результат в файл: если `output_path` не указан, создаёт файл в `outputs/story_<дата-время>.md`.
    - Дополнительно сохраняет сырой запрос и ответ в `logs/generation_<дата>.json` для отладки.
    - Возвращает путь к сохранённому файлу и сам текст.

- [ ] **2.5 Скрипт для ручной генерации `generate.py` (CLI)**
  - Принимает аргументы:
    - `--input` – путь к JSON-логу (обязательный).
    - `--output` – куда сохранить рассказ (опционально).
    - `--genre` – выбор жанра (опционально, по умолчанию из конфига).
    - `--max-events` – максимальное количество событий (опционально).
  - Вызывает `story_generator.generate_story_from_log` и выводит в консоль статус выполнения.
  - Пример: `python generate.py --input logs/raw_events_20260709.json --genre cyberpunk`

- [ ] **2.6 Интеграция с основной программой (опционально для MVP)**
  - В `main.py` (из Фазы 1) добавить флаг `--auto-generate`, который после завершения сессии (по Ctrl+C) автоматически вызывает генерацию, если сервер LM Studio доступен.
  - В противном случае предлагает пользователю запустить генерацию позже через скрипт.

- [ ] **2.7 Тестирование качества генерации**
  - Подготовить тестовый лог (например, записать 20 событий из какой-нибудь игры с диалогами).
  - Запустить генерацию с разными моделями (Qwen 1.5B, Mistral 7B) и сравнить качество.
  - Настроить параметры температуры и `max_tokens` для достижения связности (слишком высокая температура – бред, слишком низкая – сухой пересказ).
  - Документировать рекомендуемые настройки для каждой модели в `README`.

- [ ] **2.8 Обработка длинных логов (контекстное окно)**
  - Если событий больше, чем может обработать модель (например, 150 событий при контексте 4K токенов), реализовать **суммаризацию**:
    - Сначала генерировать краткое резюме для блоков событий (например, по 10 событий), затем на основе резюме строить итоговый рассказ.
    - Это сложнее, можно отложить на Фазу 4, но в Фазе 2 хотя бы предусмотреть ограничение и выдавать предупреждение, если лог слишком большой.

- [ ] **2.9 Логирование и мониторинг**
  - Все вызовы LM Studio логировать в `logs/lm_studio_calls.json` с временем, количеством событий, длиной ответа, временем ответа.
  - Это поможет позже оптимизировать промпты и настройки.

#### Результат фазы 2:
- Готовый консольный генератор, который умеет превращать JSON-лог в красивый литературный рассказ.
- Гибкая система промптов с поддержкой разных жанров.
- Стабильная работа с LM Studio через HTTP, с обработкой ошибок.
- Возможность запускать генерацию как отдельно, так и автоматически после сессии.
- Полная документация по настройке LM Studio и выбору модели.

### Фаза 3 – Графический интерфейс (GUI) и пользовательский движок (7–10 дней)

**Цель:** Создать полноценное десктопное приложение на PySide6, которое заменит консоль. Пользователь должен иметь возможность запускать/останавливать запись событий, просматривать историю сессий, настраивать параметры генерации, редактировать готовые тексты и экспортировать их. Весь тяжелый труд (OCR и LLM) должен работать в фоновых потоках, чтобы интерфейс всегда оставался отзывчивым, а игра не тормозила.

---

#### Задачи:

- [ ] **3.1 Архитектура главного окна (MainWindow)**
  - Разработать макет с использованием `QVBoxLayout` и `QHBoxLayout`.
  - Основные зоны окна:
    - **Верхняя панель (Toolbar):** Кнопки «▶ Старт» / «⏹ Стоп», «⚙ Настройки», «❓ Помощь».
    - **Центральная зона (Tab Widget):**
      - Вкладка **«Сессии»** — список всех сохранённых логов (дата, время, количество событий, статус: «Не обработан» / «Готов к генерации» / «История создана»).
      - Вкладка **«Текущая сессия»** — сырые события в реальном времени (как консольный лог, но в красивом QTextEdit с прокруткой).
      - Вкладка **«Библиотека историй»** — список сгенерированных рассказов с возможностью открыть их для чтения.
    - **Нижняя панель (Status Bar):** Статус подключения к LM Studio (зелёный/красный индикатор), текущее состояние (Idle / Recording / Generating).

- [ ] **3.2 Многопоточное ядро (Core Threads) — самое важное**
  - Создать классы-воркеры (наследники `QThread`), чтобы не блокировать GUI:
    - **`CaptureWorker`** — содержит весь цикл из Фазы 1 (захват, хеши, OCR). Передаёт события в главный поток через сигналы `pyqtSignal(str, str)`.
    - **`GenerationWorker`** — содержит вызов `story_generator.py`. Передаёт промежуточные статусы (прогресс) и финальный текст через сигналы.
  - Реализовать «мягкую» остановку потоков через флаги `self.is_running = False`, чтобы при нажатии «Стоп» цикл завершался корректно (сохранял буфер).
  - *Важно:* Воркеры должны запускаться только тогда, когда приложение свёрнуто в трей (см. пункт 3.5) — это экономит ресурсы, если пользователь не смотрит в окно.

- [ ] **3.3 Модуль `session_manager.py` (управление сессиями)**
  - Связан с `event_logger.py` из Фазы 1.
  - При старте записи создаёт новую сессию с уникальным ID (например, `session_20260709_153022`).
  - Все события, приходящие из `CaptureWorker`, складываются в эту сессию в памяти и параллельно пишутся в JSON (автосохранение каждые 30 секунд).
  - При остановке записи сессия помечается как «завершённая» и появляется в списке на вкладке «Сессии».
  - Предоставляет модели данных для `QListView` (отображение списка сессий с сортировкой по дате).

- [ ] **3.4 Окно настроек (Settings Dialog)**
  - Вкладка **«LM Studio»**:

#### Задачи (в порядке приоритета):

- [ ] **4.1 Умная фильтрация и дедупликация событий (P0 – критично)**
  - **Проблема:** OCR может выдавать почти одинаковые строки с небольшими вариациями (например, «Привет, странник» и «Привет, странник!»). В логе накапливается много шума, который захламляет промпт и может сбивать модель.
  - **Решение:** Написать модуль `deduplicator.py` с функциями:
    - `normalize_text(text)` – удаляет лишние пробелы, приводит к нижнему регистру, убирает знаки препинания для сравнения (но не для хранения оригинала!).
    - `levenshtein_ratio(a, b)` – вычисляет процент схожести двух строк (через `rapidfuzz` — предпочтительнее `python-Levenshtein`, так как не требует компиляции C-расширений при установке на Windows; либо `difflib` как совсем лёгкий вариант без доп. зависимостей).
    - `filter_similar_events(events, threshold=0.85)` – проходит по списку событий и удаляет те, которые имеют схожесть > threshold с предыдущим сохранившимся событием. При этом сохраняет более «полную» версию (если одна строка длиннее, то она, вероятно, содержит больше информации).
    - *Дополнительно:* Удалять события короче 4 символов (почти всегда шум) – но сделать порог настраиваемым.
  - **Интеграция:** Встроить вызов `deduplicator` в `event_logger.py` перед записью в JSON (чтобы хранить уже очищенные логи) и в `prompt_builder.py` перед формированием промпта (двойная страховка).

- [ ] **4.2 Выделение именованных сущностей (NER) для улучшения промпта (P1 – высокая важность)**
  - **Проблема:** Модель не знает, как зовут главного героя или ключевых NPC. В промпте события выглядят как безличные действия, что снижает связность.
  - **Решение:** Добавить модуль `entity_extractor.py`, использующий лёгкую библиотеку `spaCy` (модель `ru_core_news_sm`) или регулярные выражения для поиска имён собственных (с большой буквы в контексте).
  - **Алгоритм:**
    - Сканирует все события лога.
    - Собирает все слова с заглавной буквы, не стоящие в начале предложения (для русского языка есть нюансы, но это сработает для имен и названий).
    - Группирует частотность – если имя повторяется больше 2 раз, заносит его в список «Ключевые персонажи».
    - Также ищет маркеры локаций: «в городе», «в таверне», «замок» – сохраняет названия.
  - **Интеграция в промпт:** Обогащает системный промпт фразой: *«Главный герой – [имя персонажа, если найдено]. Действие происходит в [локация]. Вот список действующих лиц: [список имен]. Используй эти имена в рассказе.»* – это резко повышает качество генерации.

- [ ] **4.3 Динамическое обрезание контекста (умный выбор событий) (P1 – важность)**
  - **Проблема:** Если игровая сессия длится 3 часа, лог содержит 500–1000 событий. Модель с контекстом 4K токенов не вместит все.
  - **Решение (два подхода, комбинируем):**
    - **Семплирование по времени:** Разбить временную шкалу на равные интервалы (например, по 5 минут) и брать из каждого интервала только самое «интересное» событие (самое длинное или с наибольшим количеством новых имен).
    - **Семплирование по значимости:** Присвоить каждому событию «вес»: диалоги с NPC важнее, чем сообщения о луте. Реализовать простой эвристический классификатор (по ключевым словам «квест», «диалог», «выбор»).
  - **Модуль `context_selector.py`:** Принимает список событий и максимальное допустимое число токенов (вычисляем приблизительно как len(text)/4). Возвращает сокращённый список, сохраняя хронологию и ключевые точки.

- [ ] **4.4 Режим «Редактор событий» в GUI (P1 – удобство)**
  - **Идея:** Пользователь может зайти в уже завершённую сессию, посмотреть список сырых событий и вручную удалить/отредактировать некоторые строки перед тем, как нажать «Сгенерировать». Это даёт ему контроль над сюжетом.
  - **Реализация:**
    - На вкладке «Сессии» добавить кнопку «Редактировать события» для выбранной сессии.
    - Открывается диалоговое окно с `QListWidget`, где каждое событие – строка с чекбоксом (для удаления) и полем для редактирования (двойной клик делает ячейку редактируемой).
    - После сохранения изменений обновляется JSON-лог сессии (создаётся резервная копия оригинала).

- [ ] **4.5 Генерация «мета-описаний» (настроение, погода, время суток) (P2 – по желанию)**
  - **Идея:** Чтобы рассказы звучали более атмосферно, извлекать из скриншотов не только текст, но и визуальные признаки: яркость (день/ночь), цветовая гамма (тёплая/холодная), наличие красных тонов (бой).
  - **Технически:** Добавить в `screen_capture.py` функцию `analyze_scene(image)`, которая считает среднюю яркость и доминирующий цвет. Сохранять эти данные как мета-теги в лог (рядом с текстом).
  - **В промпте:** использовать фразы: *«Действие происходит ночью, вокруг царит мрачная атмосфера»* или *«Яркое солнце заливает поле битвы»* – это добавит живости.

- [ ] **4.6 Расширенный экспорт: PDF и Markdown с иллюстрациями (P2 – для «вау-эффекта»)**

  - **Markdown:** Улучшить существующий экспорт – добавить в начало `YAML`-frontmatter с метаданными (для совместимости с Obsidian).
  - **Иллюстрации (опционально):** В будущем можно добавить кнопку «Добавить скриншоты» – во время записи приложение сохраняет не только текст, но и несколько ключевых скриншотов (например, при срабатывании детектора изменений) в папку `outputs/screenshots/`, а в экспорте вставлять их между абзацами (по нажатию).
  - ⚠️ **Политика хранения:** без ограничений папка `outputs/screenshots/` будет расти неограниченно при частых длинных сессиях. Добавить лимит (например, автоочистка скриншотов старше N дней или ограничение по суммарному размеру папки) и предупреждение в настройках.
  - ⚠️ **Приватность:** захват идёт по всему окну/экрану — если поверх игры открыт Discord, стрим-оверлей или чат с личными данными, это может попасть в скриншот и затем в текст, которым пользователь поделится в соцсетях. Стоит добавить предупреждение в README и, по возможности, опцию исключения определённых окон/оверлеев из захвата.

- [ ] **4.7 Интеграция с TTS (озвучка рассказов) – «бонусная фишка» (P3 – если останется время)**

- [ ] **5.1 Профилирование производительности (бенчмарки)**
  - **Цель:** Замерить реальное потребление ресурсов в различных сценариях и выявить узкие места.
  - **Инструменты:** `cProfile` (встроенный профайлер Python) + `memory_profiler` для отслеживания RAM.
  - **Сценарии тестирования:**
    1. **Фоновый режим (без активного OCR):** Игра запущена, приложение свернуто в трей, только захват и хеширование (частота 0.2с). Замерить CPU (%) и RAM (MB) в течение 10 минут на рабочем ПК (слабый) и домашнем (мощный).
    2. **Активный режим (OCR запущен):** Искусственно вызвать частые изменения экрана (например, быстро листать диалоги). Замерить нагрузку CPU, RAM и время отклика интерфейса.

- [ ] **5.2 Оптимизация на основе профилирования**
  - **Снижение частоты захвата:** Если в фоновом режиме CPU > 10% на слабом ПК, увеличить интервал между хешами до 0.3–0.5 сек (это все равно ловит 99% событий).
  - **Асинхронная обработка:** Если OCR работает слишком медленно на слабом ПК, вынести его в отдельный процесс (не поток) с низким приоритетом, чтобы не тормозить игру. Использовать `multiprocessing` (но это сложнее; можно оставить как опцию в настройках).
  - **Сжатие скриншотов:** В кольцевом буфере хранить не полные скриншоты, а уменьшенные копии (например, 640x360) – этого достаточно для OCR и хешей, а памяти тратится в 3 раза меньше.

  - **Методика:**

## 3. Технические решения с учётом вашего окружения

| Пункт | Решение |
|-------|---------|
| **Язык** | Python 3.11.5 (совместим с вашей версией) |
| **IDE** | VS Code + GigaCode (поможет генерировать шаблоны кода) |
| **Связь с LLM** | Через HTTP-запросы к локальному серверу LM Studio (`http://localhost:1234/v1/chat/completions`). Это позволяет легко переключать модели и не париться с биндингами. |
| **Работа на слабом ПК** | Только `mss` + `pytesseract` (CPU). Модель **не грузится** в память. |
| **Работа на мощном ПК** | Запускаем LM Studio с моделью в квантовании **GGUF Q4_K_M** (требует ~6–8 ГБ VRAM для 7B; для fp16 без квантования нужно ~14 ГБ, что не подходит). Генерация – только по запросу. |
| **Хранение** | JSON + опционально SQLite для быстрого поиска по датам. |
| **GUI** | PySide6 – нативная отрисовка, легче по памяти, чем Tkinter. |

## 4. Возможные риски и как их избежать

- **OCR плохо читает шрифты** – добавить предобработку (увеличение контраста, преобразование в градации серого) через OpenCV.  
- **Слишком большой лог** – ограничивать количество событий (например, последние 500) при формировании промпта.  
- **LM Studio не запускается автоматически** – в документации указать, что пользователь должен заранее запустить сервер. В будущем можно добавить автоматический запуск через subprocess.  
- **Зависания GUI во время генерации** – обязательно выносить запрос к LM Studio в отдельный поток с отображением индикатора прогресса.  
- **Несовместимость зависимостей с новой версией Python** – зафиксировать Python 3.11.5.
- **Эксклюзивный полноэкранный режим не захватывается `mss`** – в README сразу рекомендовать пользователю режим "оконный без рамки" (borderless windowed) как основной сценарий использования.  
- **Неограниченный рост `outputs/screenshots/`** – добавить лимит хранения/автоочистку.  
- **Захват приватного контента (Discord/чаты поверх игры)** – предупредить в README, что в кадр может попасть всё, что открыто поверх игры.  
- **Ломающиеся изменения формата JSON-лога между фазами** – добавить поле `schema_version` с самого начала.
