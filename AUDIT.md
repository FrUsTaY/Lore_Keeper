# Аудит проекта «Нарративный Архивариус» (Lore Keeper)

Данный документ содержит результаты аудита кодовой базы приложения. Основной фокус аудита: архитектура, производительность, ресурсоемкость, потокобезопасность и чистота кода.

## 1. Архитектура и Разделение логики (GUI vs Backend)

### Наблюдения:
- Приложение имеет разделение на GUI (`src/gui/main_window.py`) и бэкенд (`src/`), но есть места, где бизнес-логика и управление состоянием слишком сильно связаны с интерфейсными потоками (Workers).
- **Патчинг логгера (Monkey-Patching)**: В `CaptureWorker.__init__` (`src/gui/workers.py`) используется перехват метода логгера (`self.trigger_manager.logger.log_event = intercepted_log`). Это "грязный" хак, который создает сильную связность между UI-компонентом и низкоуровневым классом логгера.
- Прямой доступ к внутренним компонентам: Например, в `MainWindow.on_settings_saved` происходит прямое обращение к `self.capture_worker.trigger_manager.min_volume_db`.

### Рекомендации:
- [x] **Использование паттерна Observer**: Убран monkey-patching `log_event`. Внедрен `on_new_event_callback` в `EventLogger`, который `CaptureWorker` использует для подписки и безопасного проброса в GUI через сигналы.
- [ ] **Инкапсуляция настроек**: GUI не должен изменять поля внутренних объектов напрямую. Следует добавить метод `update_settings(config_manager)` в `TriggerManager` и `CaptureWorker`.

## 2. Потокобезопасность (Thread Safety) и Очистка ресурсов

### Наблюдения:
- **Очистка ресурсов WASAPI (PyAudioWPatch)**: При остановке записи (`CaptureWorker.stop()`) вызываются `trigger_manager.stop()`, а затем `transcriber.stop()` и `audio_capture.terminate()`. В `AudioCapture.stop_stream()` закрывается стрим. Однако метод `record_chunk` может "повиснуть", ожидая данных, если не проверять флаг `is_running` внутри самого цикла чтения. Переданный `is_running_callback` помогает, но нужно убедиться, что он прерывает блокирующие вызовы или что блокировки кратковременные.
- **Остановка очередей**: В `AudioTranscriber.stop()` есть правильный подход — отправка `None` в очередь, чтобы разблокировать `self.queue.get(timeout=1.0)`.
- **Зависание GUI при остановке**: Метод `MainWindow.quit_app()` вызывает `self.capture_worker.wait()` в главном потоке. Если воркер повис из-за неотвечающего устройства или блокировки очереди, приложение не закроется и останется висеть "зомби-процессом".

### Рекомендации:
- [x] **Безопасное завершение аудио-потока (Без зависания)**: В `quit_app()` добавлен таймаут (`wait(2000)`) на ожидание завершения потоков воркеров с последующим принудительным `terminate()`. Это предотвращает "зомби-процессы".
- [x] **Thread-safe передача данных**: Убедились, что все взаимодействия (включая ошибки) идут строго через Qt Signals (`Signal.emit()`).

## 3. Производительность и Ресурсоемкость

### Наблюдения:
- **Сохранение временных файлов**: `AudioTranscriber` сохраняет каждый кусок аудио в `outputs/temp_audio/` как `.wav` файл перед отправкой в Groq или локальный Whisper, а затем удаляет в блоке `finally:`. Если процесс аварийно завершится (например, `SIGKILL`), эти файлы останутся.
- **Оптимизация чтения сессий**: `SessionManager.get_all_sessions()` парсит все JSON-файлы логов. Имеется базовая оптимизация через кэширование по `mtime`, что очень хорошо для производительности GUI, когда файлов становится много.
- **Отложенная инициализация моделей**: В `AudioTranscriber._process_queue` локальная модель Faster-Whisper инициализируется отложенно в фоновом потоке, что является отличным решением против зависания GUI.

### Рекомендации:
- [ ] **Очистка мусора (Garbage Collection) аудио-файлов**: Добавить функцию для надежного поиска и удаления старых `.wav` файлов-сирот (оставшихся после крашей) в `outputs/temp_audio/`.
- [ ] **In-Memory передача для Groq**: Если Groq API и локальный Faster-Whisper поддерживают передачу аудио в виде байтовых потоков (bytes/BytesIO), стоит рассмотреть отказ от записи временных `.wav` файлов на диск. Это сэкономит ресурс SSD и ускорит обработку.

## 4. Обработка исключений (Error Handling) и Сеть

### Наблюдения:
- **Groq API и Отказ Сети**: В `GroqClient.generate` и `transcribe_audio` реализована базовая система повторных попыток (retries) и `raise_for_status()`. Если сеть недоступна, выбрасывается `Exception`, который ловится в `GenerationWorker.run` (или `AudioTranscriber._process_queue`) и через сигнал передается в GUI.
- **Молчаливое падение в Transcriber**: В `AudioTranscriber._process_queue` ошибки транскрибации ловятся `except Exception as e`, печатаются в консоль (`print`) и поток засыпает на 2 секунды. При этом GUI никак не уведомляется о том, что транскрибация сломалась (например, из-за неверного токена или блокировки по Rate Limit). Пользователь будет видеть статус "Recording", но текст появляться не будет.

### Рекомендации:
- [x] **Уведомления об ошибках в GUI**: В `AudioTranscriber` добавлен `on_error_callback`, который пробрасывается вверх через `TriggerManager` к `CaptureWorker`, откуда испускается сигнал `transcription_error(str)` для отображения пользователю проблем с интернетом или токеном.
- [ ] **Использование стандартного `logging`**: Заменить большинство вызовов `print()` на `logging.info`, `logging.warning` и `logging.error` для стандартизации логов и удобства отладки "в поле".

## 5. Тестирование

### Наблюдения:
- В проекте есть тесты (`pytest tests/`). Прогон показал **34 успешных теста**.
- Покрытие (`coverage`) хорошее для ядра (100% для EntityExtractor и TimeSegmenter, ~95% для Deduplicator).
- Покрытие GUI, потоков (Workers) и API клиентов (Groq, LM Studio) очень низкое (10-20%), что типично, но является зоной риска.

### Рекомендации:
- [ ] Написать мок-тесты для `CaptureWorker` и `AudioTranscriber`, чтобы протестировать логику отработки сетевых ошибок (Groq API error) и убедиться, что очереди и ресурсы корректно высвобождаются при крашах.

---
**Итог:** Архитектура в целом жизнеспособна, но требует небольшого рефакторинга в слое связывания интерфейса и бизнес-логики (убрать monkey-patching), а также более "отзывчивой" обработки ошибок фоновых потоков (передача статуса ошибок транскрибации обратно в GUI).
